# 1. 项目背景

在实时交易系统中，资金的一致性要求很高，如果出现商家资损、用户资损都是比较严重的问题，在支付链路中防范是最基本的，但是在支付链路之外也需要一定的旁路校验方案：
- T+1对账；（时延较高，如果出现漏洞，发现时可能已经出现大面积损失）
- <font color="#f79646">准实时规则校验</font>；（时延较低，可以在分钟级别发现问题，从而介入止损）

BCP项目（Business Check Service）所提供的服务：根据业务链路中的日志，定制不同日志间的一致性规则，实现准实时规则执行来识别异常；
- 日志解析：用户可以指定日志（通过关键字），解析为特定的JSON格式；
- 日志匹配：将解析后的JSON日志，通过关键字进行匹配关联；
- 核对规则：用户可以配置一定的规则，来对多个日志进行核对；

核心目标就是<u>通过可配置化的细粒度规则，基于日志来准实时地校验支付链路是否正常</u>；
- **实时性**：分钟级异常检测；
- **准确性**：覆盖全链路交易类型，规则可灵活配置；
- **自动化**：异常自动告警，减少人工介入。

# 2. 整体技术方案

![](/images/projects-bcp-architec.webp)

- **架构**：基于Flink的实时流处理 + 分布式任务调度 + 日志/规则元数据配置 + 规则执行；
- **核心组件**：
    - **Flink集群**：实时清洗日志，过滤出已有的规则所关心的日志，并清洗为特定的易解析的格式；
    - **Redis**：存储高频访问的待核对消息；
    - **MySQL**：存储开发运营人员配置的规则元数据、工单任务及结果；
    - **Kafka**：日志数据消息队列。
- **数据流**：
    交易日志 → Flink清洗 → 标准化消息 → Redis/MySQL → 规则引擎核对 → 告警/结果存储。

# 3. 业务核心模块

## 元数据管理模块

功能性服务：

- 用户定义消息解析规则；用于将用户服务的特定日志解析为JSON格式（清洗）；
- 消息增删改查管理；
- 元数据分类：
	- 触发消息元数据：触发消息通常为一条支付链路中完成的消息；如支付的回调消息；（一个规则通常是从「触发消息」开始匹配整个链路的其他日志，再完成核对）
	- 核对消息元数据：通常为一条支付链路中的支付、退款等起始消息；

![解析示例](/images/projects-bcp-log-parse.webp)

## 日志清洗模块

用户配置的元数据会被导入Redis中，日志通过Kafka导流后，在Flink中执行过滤、解析、存储：
1. 过滤：过滤出元数据关心的日志；
2. 解析：按照用户的配置，解析日志为JSON格式；
3. 存储：将解析完成的消息，存储在MySQL或Redis中；
	- 触发消息存储在MySQL：一个触发消息对应着一次核对任务的开始，需要更高的可靠性；
	- 核对消息存储在Redis：核对消息的生命周期较短，不需要持久化；

## 规则管理模块

功能性服务：
- 日志关联：在已经配置的元数据消息中，用户需要指定日志之间的匹配关系，通常以解析后的日志的某个字段进行关联（如交易流水号、traceId等）；
- 规则执行：关联的消息之间，需要执行什么逻辑。如：<font color="#f79646">字段之间组合计算</font>，订单总金额通过优惠券扣减后，应该等于最终支付金额，如果不相同，则告警；

规则中可用的操作符：
- `if`条件
- 计算符号：`+`、`-`、`*`、`÷`、`=`、`≥`、`≤`、`>`、`<`、等简单计算；
- 区间值；
- 字典值；如交易状态、结果、渠道枚举等；
假设现在有支付消息payActionMessage、回调消息callbackMessage2个消息，设置了一个规则：`如果支付成功，则检查：支付成功的回调消息的「用户支付金额」 = 支付消息 - 优惠券金额`
```java
if (callbackMessage.status == "SUCCESS") {
	payActionMessage.totalAmout - payActionMessage.couponAmount == callbackMessage.amout;
}
```

执行逻辑：
1. 规则的执行是在后端服务中；
2. 后端服务启动时，会预热一些规则到分布式缓存中；
3. 每个后端服务都会启动一个独立的分布式调度服务，抢占DB中的「待核对的触发消息」工单；抢占成功后，则执行对应的规则；
4. 根据日志关联，从Redis中获取匹配的日志，在内存中，根据规则执行计算、核对。
5. 核对失败则触发告警。成功则忽略；


# 4. BCP的工作流

本质就是多节点同时抢占DB的中任务，抢到则执行，执行失败则将任务更新后释放，可再次被抢占执行。

## 业务的工作流程

工作流程：参考下图
 1. Flink根据元数据配置，对日志清洗，<font color="#4bacc6">将触发消息创建一个工单任务到DB中</font>，普通消息放入缓存；
 2. 消息校验服务会<font color="#4bacc6">定时轮询DB中的未处理完成的工单任务</font>。通过<font color="#4bacc6">抢占式</font>的方式抢占DB中的任务，抢占成功，则执行该工单任务；
 3. 校验服务根据任务中的元数据配置、匹配规则，从Redis中拉取匹配的所需要核对的消息。
 4. 在内存中，根据具体的核对规则，完成不同日志消息间对应的字段的计算，对于计算结果不满足的任务，执行对应的告警；

![](/images/projects-bcp-architec.webp)
## 工单调度的核心流程

首先定义什么是一个工单任务：
1. 工单任务是一个<font color="#9bbb59">单独的消息核对任务</font>，对应单次的日志；比如<u>一条支付链路，对应一个任务</u>。
2. 工单任务定义了类型，比如支付链路任务、退款、营销活动等等；定义类型的目的是区分不同任务的业务体量，方便针对性的对特定类型的任务增加调度资源；

![](/images/projects-bcp-worker-db.webp)

调度的执行过程：
1. 每个后端阶节点启动上线时，会到「心跳注册表」中注册上线信息；主要就是将hostname注册到这张表中，并设置状态为<font color="#4f81bd">上线状态</font>
2. 每个节点同时会开启2个定时任务：
	- <font color="#f79646">心跳更新定时线程任务</font>：定时5min向「心跳注册表」更新自己的最新状态、更新时间；表明在线；
	- <font color="#f79646">下线检测定时线程任务</font>：可能存在某些机器宕机，那么就需要定时任务（10min）实时检查这个心跳表中有没有超时未更新的节点，如果有则置为「下线状态」，并将这个节点所持有的所有工单任务释放；
3. 完成注册后，节点就会开始执行核对任务，会有3个单线程任务执行：
	- <font color="#f79646">单线程抢占任务</font>：节点每隔2min，执行一次抢占任务，抢占`lock_flag`为空的任务，最大抢占任务量为100；
	- <font color="#f79646">单线程加载任务</font>：节点每隔2min，执行一次任务拉取，拉取自己节点抢占了的任务，加载进内存中的<font color="#4bacc6">任务队列</font>中；
	- <font color="#f79646">单线程分发任务</font>：此线程会不断轮询消费<font color="#4bacc6">任务队列</font>，根据任务的类型，分发给指定的业务线程池，由对应的线程池执行真正的核对任务的处理；
4. 业务线程池：根据`task_type`在程序启动前配置在配置文件中，启动时根据配置文件实例化好对应的业务线程池；
	- 任务执行成功，则将对应的工单设置为成功；
	- 任务执行失败，则将对应的工单设置为重试状态，并释放此工单，由所有节点再次抢占执行；
	- 任务到达最大重试次数，则将工单设置为失败；

其中具体的任务是在规则模块中由用户配置：日志间字段的匹配，同时支持数字的简单计算；

## 为什么选择此方案

1. 高可靠性：
	- 工单持久化存储，不会数据丟失；
	- 工单支持重试；
	- 节点宕机自动故障转移，分布式节点调度，不依赖任何单一的节点；节点宕机也不会丢数据，不会影响被其他节点调度；
2. 灵活性：
	- 工单支持时延重试，对于实时性高的任务，延迟时间可以尽可能短，对于实时性低的任务，可以增加延迟时间；
	- 重试次数、重试间隔，都可以根据任务类型设置；

不使用MQ的原因：
- Kafka不支持延迟消息，不支持自定义重试间隔，重试次数；
- RocketMQ支持延迟消息，不支持自定义重试间隔，重试次数；
- 同时消息队列的重试，通常阻塞后续任务消费；
- 消息队列的可靠性不如数据库；
- BCP并不是RT敏感型任务，不需要太低的RT，更看重可靠性；

# 5. 项目业务指标

BCP的性能考量主要是：
1. TPS：BCP的业务是按完整的日志产生、清洗、存储、执行核对，这一整条链路算做一次事务，因此使用TPS作为衡量指标；
2. 时延：作为准实时的旁路校验系统，要尽可能快的发现问题；
3. 可靠性：正在执行任务的节点如果宕机，需要有机制故障转移，能够释放工单，继续由其他节点执行；
## TPS

交易中台每天大概有3亿的日志量，Flink根据配置的消息规则，每日会匹配出1000w+的消息量；

`工单的数量 = 交易流水 * 规则数量 = 300w * 2 = 600w左右`
- 其中交易流水为交易中台每日订单数；300w左右；
- 规则数量为每个交易平均会配置1-2个规则来执行核对任务；

那么平均的TPS在：`600w / 10 * 60 * 60 = 166TPS`（10h是因为业务低峰期基本没有支付消息），白天的峰值可以到到200TPS；

## 时延

BCP作为准实时的核对系统，那么时延也是不能太高的。整个链路是从日志创建，Flink清洗，落库，任务核对。时延控制在2min内；也就是交易如果存在异常链路，可以在2min内识别并发出告警。

业界监控告警的时延一般在1min内；像阿里的Sunfire监控告警平台是实时监控日志，并没有过多的业务语义，单条日志只要不满足特定规则，则触发告警。

BCP业务有复杂的清洗、计算逻辑，2min是可以接受的。

# 6. Redis的大key发现与处理

我们的非核心消息是存储在Redis中，这类消息一般存储不会超过5min，最快2min内消费完成后，就会删除。

<font color="#fac08f">问题发现</font>：但我们的Redis内存在一次扩容的过程中，CPU突然飙升到80%，随后扩容完成后，又恢复正常。

对于这次异常的CPU飙升，我们怀疑有大key存在，通过Redis的命令`bigkeys`，查到了一个200w大小的list数据；
```bash
/redis-cli --bigkeys --i 0.1
```
- `-i` 可以指定扫描的频率，100ms执行一次，防止阻塞业务

<font color="#fac08f">问题定位</font>：查到大key后，我们并没有立即删除，因为当前的业务并没有受到影响，因此判断此key并不会影响业务，保留这个key更好的查找原因；

最终查到这个key是一个key中存在`null`字符串的大key；和交易的同学一起排查到，交易的订单状态轮询任务一直在轮询一个空的订单号，导致产生大量存在null订单的日志，Flink清洗后，拼接成key，存储到了Redis中，不断的push后，导致一个大list产生；

<font color="#fac08f">问题解决</font>：我们在业务低峰期，使用Redis的`unlink`命令删除大key，此命令会立即返回，后台异步删除key，减少阻塞

```bash
unlink large_string_key  # 优先异步删除
```
