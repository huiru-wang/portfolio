# 1.重构背景及目标

**重构背景、难点：**
1. <font color="#4bacc6">档案存储的异构</font>：人事的档案随着历史发展，存储一直是异构的，底层有多张表，还有一部分数据是从外部服务读取。这些数据一起构成了一个员工的档案；上层服务一直在理解这些存储，获取档案时，还需要理解哪个字段在哪个表，开发复杂度、新人理解成本都非常高；
2. <font color="#4bacc6">模块封装太差</font>：在系统的架构分层中，没有统一的档案域的读写入口，其他模块在执行档案的读写甚至会直接操作某个表进行读写。
3. <font color="#4bacc6">新人接手成本高，影响业务迭代速度</font>：读写入口40+，且多个入口含有不同的特殊逻辑。；
4. <font color="#4bacc6">稳定性保证</font>：花名册服务是人事业务中最核心的服务，几乎所有的模块，甚至外部调用方都依赖花名册，如何将流量平滑、稳定地切换到新的代码逻辑，很重要；

**重构的核心目标：**
1. <font color="#f79646">屏蔽异构的存储层</font>，让上层不感知各个档案字段存储在哪里，直接使用统一接口更新即可：
	- 人事档案对外提供的档案查询和写入，都只是key-value的结构，不感知底层存储；
	- 实际底层存储是异构的，存储在不同的表中、不同的服务中；
2. 易理解、易接入、易维护：新的重构代码需要做到这几点。这几点都是工程上的事情，如领域模型合理，代码逻辑清晰，注释清楚等等；
3. <font color="#de7802">流量切换要保证业务正确</font>：<font color="#f79646">40+的流量入口</font>切换到新代码，如何保证逻辑的正确性，线上业务无影响？或做到影响可控，随时切换回旧逻辑；
	- 历史遗留原因，档案的写入口很多，且不同入口含有一些特殊逻辑；
	- 历史代码包袱很重，动不动就一个方法200+行代码，很难不有遗漏的逻辑；
	- 因此要有一套黑盒机制，能够做到<font color="#f79646">数据对账</font>；即使完全不懂原来的代码逻辑（假设），也要能通过对账来发现问题。

# 3.异步实时对账逻辑设计

## 为什么需要对账

本次重构，对账逻辑是要优先设计出来，因为业务不正确，重构没有意义。

要先设计一套，无论怎么重构，<font color="#d99694">保证新旧的档案更新链路中，任意字段更新结果不一致，都能准确发现</font>。

如果是从<u>代码内部逻辑的正确性来确认链路的正确性</u>，是完全没有说服力的，也是不可行的，因为没有人能保证一个复杂大型应用的重构的每一个细节都关注并熟悉到，甚至与还有一些团内内都无人知晓的特殊逻辑存在。

<font color="#d99694">所以，要设计一套对账，把原来的代码当成黑盒，不理解内部更新逻辑，只关注更新结果的正确性</font>。

## 黑盒对账逻辑的实现

![](/images/hr-saas-roster-data-check.webp)

黑盒对账逻辑：
1. 在每一个档案更新的入口处，先执行「新档案更新逻辑」，新逻辑在数据落库之前增加<font color="#d99694">「切流开关」</font>，在对账期间，开关关闭，新逻辑不会真正落库；将新逻辑执行的结果存入缓存；
2. 再执行「旧档案更新逻辑」，此时「切流开关」关闭，旧逻辑正常完成更新落库，并将落库结果发送到「mq」中；
3. mq异步消费到档案更新事件，根据「traceId」从缓存中获取对应的「新逻辑执行结果」，完成字段级别的数据比对；
4. 任意字段结果不一致，则发出告警；
5. 全部字段结果一致，则忽略；
6. 上述逻辑在线上稳定运行，不存在报警之后（7天），打开「切流开关」，完成流量切换，则此更新入口的切流完成。
7. 多个档案更新入口，重复以上操作，多个入口之间可以并行操作以上逻辑（增加个对账入口标识即可）；

> 此对账，不关心内部逻辑，只关心结果，出现不一致再查看原因，稳定性更好，效率更高。

# 4.档案模型设计

同一档案领域模型：<font color="#d99694">企业档案元数据 + 员工档案值</font>

1. 企业档案元数据：存储企业的档案字段的配置，通常包含以下内容：
	- `fieldCode`：字段唯一id；
	- `fieldType`：字段类型（文本、选项、时间、数字等）
	- `fieldName`：字段的显示名称；
	- `source`：标识字段来源（系统、用户自定义）；
2. 员工档案值：员工的档案内容，本质上是企业档案元数据的`<fieldCode, fieldValue>`表；

将员工数据，填充进企业的档案元数据，则构建出员工的档案模型：

![](/images/hr-saas-roster-employee-roster.webp)

至此，档案的读写模型已经可以确定：
- 读模型：企业元数据 + 员工档案，构建出带有字段元数据的档案模型；
- 写模型：只需要写入key-value格式的数据；

# 5.异构存储的路由设计

首先明确的是路由的是什么：路由的是档案的每一个字段；比如（职位、手机号、学历等等），他们都可能在不同的表、甚至不同的服务；

设计的目标：
1. 在上层业务的视角中，<font color="#f79646">不需要理解异构的存储</font>，只有要查询、更新的字段；比如要查询某个字段，不需要关系从哪个表中取哪个字段；
2. 路由层根据档案字段，映射到对应的DAO；
3. 对于系统字段，也就是固定每个企业都有的字段，在代码中以<font color="#f79646">枚举</font>的方式维护。对于企业自定义的字段，则固定存储到自定义表中；

![](/images/hr-saas-esign-model.png)

花名册档案分为2种：
- 系统字段：系统内置的不可更改，任何企业都存在的字段；（分类存储在不同的表）
- 用户自定义字段：用户可自行创建的字段；（固定存储在一张表）

路由策略：
1. 首先是枚举出所有的数据源；（所有表、外部存储服务）
2. 针对「系统字段」，每个字段通过注解标识所存储的位置；
3. 项目启动时，解析所有的注解，本地缓存起来，结构为：`<FieldCode, DAO>`
4. 执行更新档案时，根据映射关系，获取存储服务，执行更新；
